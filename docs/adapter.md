# Feature Adapter

The feature adapter service (`FeatureAdapter`) is totally independent from the GVE rendition web component. It can be used by consumer code to _adapt_ the features found in its data to the set used in the rendition component. This way, scholars can use higher-level taxonomies (e.g., `epigram-nr`, `correction-type`) without worrying about rendition details.

The feature adapter service itself just deals with a received array of features. It does not need to know anything about their source. Its only task is returning a new array with adapted features. Features here just include a name and a value, ignoring any other properties.

So, the adapter is designed to be used before passing data to the web component:

```txt
Backend Data → DataFeatureAdapter → Adapted Data → Web Component
```

The web component remains unchanged and unaware of the adapter. This maintains separation of concerns and allows the adapter to be optional.

## Usage Context

The adapter service is typically used by another service (`DataFeatureAdapter`) whose task is to get data targeted to the GVE rendition web component and create a copy of it where all the feature sets in it (except those belonging to operation's metadata) have been adapted.

> ⚠️ Operation features under data's steps items (`steps[i].operation.features`) are _not_ affected by the adapter, because these features are not used by the GVE rendition web component and they reflect the original features with additional metadata we want to preserve. Features affected belong to step's feature sets and to nodes in `taggedNodes`, which are both used by the component for rendering.

This `DataFeatureAdapter` must adapt all the features included in data, except those linked to each operation definition under `steps` (`steps[0].operation`, `steps[1].operation`, etc.). So, its logic is finding all the feature sets which need to be adapted, and leverage an instance of `FeatureAdapter` to adapt them, as follows:

1. get as input the data received from the backend.
2. make a copy of this data so to leave the input data untouched.
3. process the copy by adapting all the features found in it, i.e.:
   - for each item in the `steps` array, process:
     - the set of features in array `featureSet.features`;
     - the set of features of each node in map `featureSet.nodeFeatures`.
   - for each version key in `taggedNodes`, process the features set of each node in the version's array of nodes. The `taggedNodes` map has one property per version tag, which is an array of nodes; each node has an array of features under `features`.
4. pass the adapted data to the web component, rather than the original one.

So, this is completely opaque to the web component. This is just a utility tool which can be used by consumers of this web component.

This adapter starts with a set of features, and transforms it into another set of features. So, it is completely transparent to the component, and is applied to data which feed it before they are passed to the component itself. In data, each step generated by executing an operation generates a new text version with its `featureSet`. So, the adapter can be applied to data by transforming the features contained in each set.

This can be useful when data have higher-level features which can be translated into lower-level so that they can be rendered by the component.

For instance, one might have a generic, higher-level feature named `epigram-nr` with value equal to `12` attached to the first character of the base text, and translate it into lower-level features representing a number added to the top-left corner of that character:

- `r_hints`=`note`: use hint with ID `note`.
- `r_hint-vars`=`note=12`: set the `note` variable of the hint to `12`.
- `r_h-position`=`nw`: override the hint's position to `nw`.
- `r_h-offset-y`=`-10`: override the hint's Y-offset to `-10` (up).
- `r_h-offset-x`=`-15`: override the hint's X-offset to `-15` (left).
- `r_h-scale-x`=`2`: double the width of the hint with reference to the bounding rectangle of the reference character, or it would be too narrow to fit a number without distorting the number to display.

## Feature Adapter Logic

The feature adapter works in two steps:

1. **match** the features which must be adapted.
2. **process** each match.

Both these steps are configured by the adapter settings.

### 1. Feature Adapter: Feature Matching

Features to be matched. These are defined by a small DSL with this syntax:

- 1 or more **clauses**, separated by logical operators: `AND`, `OR`, `AND NOT`, `OR NOT`. These follow the standard precedence in boolean algebra: so first NOT, then AND, then OR.
- **whitespace** separate tokens.
- clauses can be grouped with **brackets** `()` for precedence.
- each **clause** has format:
  1. **name**: the feature name.
  2. **operator**: the value comparison operator to use. This can be:
     - `=` equals.
     - `!=` not-equals.
     - `^=` starts-with.
     - `$=` ends-with.
     - `*=` contains.
     - `?=` matches-wildcards `?` and `*`.
     - `~` matches-pattern: matches regular expression.
     - `==` numeric-equals: first cast to numeric value, and if this succeeds compare for equals, else return false.
     - `<>` numeric-not-equals: first cast to numeric value, and if this succeeds compare for equals, else return false.
     - `>` numeric-greater-than: first cast to numeric value, and if this succeeds compare for greater-than, else return false.
     - `<` numeric-less-than: first cast to numeric value, and if this succeeds compare for less-than, else return false.
     - `>` numeric-greater-than-or-equal: first cast to numeric value, and if this succeeds compare for greater than or equal, else return false.
     - `<` numeric-less-than-or-equal: first cast to numeric value, and if this succeeds compare for less-than-or-equal, else return false.
  3. **value**: the value. Its content depends on the operator used. If the value includes spaces, it is wrapped in `""`.

In clause, operator and value can be omitted if all what we want to match is the feature name.

For instance:

- `note` matches a feature with name=`note`, whatever its value.
- `note^=corrected` matches a feature with name=`note` and value starting with `corrected`.
- `note^=corrected AND (color=red OR color=green)` matches a feature with name=`note` and value starting with `corrected` and either a feature named `color` with value equal to `red` or a feature named `color` with value equal to `green`.

**Group capture**: each clause can be wrapped in square brackets when you want to capture its name and value, similar to what happens in a regular expression when capturing groups in the matched text. So, `[note^=corrected]` means that we want to capture into a numbered group (1, 2, 3... in the order the captured clauses are specified) the name and value for the matched note feature. Then, in the feature replacement stage, we will use this number prefixed by `$` as a placeholder for the captured name or value, e.g.:

- `$1.name`=captured feature name.
- `$1.value`=captured feature value.

To **name a group**, rather than using the ordinal number, we can specify the name after `[` and before `:`. For instance, `[corr:note^=corrected]` captures the matched feature into a group named `corr`. So, in this case we would have:

- `$corr.name`=captured feature name.
- `$corr.value`=captured feature value.

### 2. Feature Adapter: Feature Processing

Whenever features are matched:

- the matched features are removed.
- a new set of features is added, from an array of strings, each representing a feature to add, with its name and value. The string has format `name=value` to set feature's name and value.

### Feature Adapter Settings Model

So the settings model is:

- `operations`: a list of adapter operations, each with these properties:
  - `pattern`: a string with the DSL representing the pattern to match, as explained [above](#1-feature-adapter-feature-matching).
  - `features`: an array of strings, each representing a feature to be added with form `name=value`. In this string there can be captured groups placeholders, e.g. `$1.value`, `$color.value`.
  - `mode`: one of `add` (default), `replace`, having this behavior:
    - `add` just adds `features`.
    - `replace` removes the matched features before adding `features` (when present; if empty, this means that we will just remove the matched features).

## Usage Example

```ts
import { DataFeatureAdapter, ProcessingMode } from "./adapter/index.js";

// Configure the adapter
const adapter = new DataFeatureAdapter({
  operations: [
    {
      // Match epigram numbers and transform to rendition hints
      pattern: "[num:epigram-nr==12]",
      features: [
        "r_hints=note",
        "r_hint-vars=note=$num.value",  // Use captured value
        "r_h-position=nw",
        "r_h-offset-y=10",
        "r_h-scale-x=2",
      ],
      mode: ProcessingMode.REPLACE,  // Remove original, add new
    },
  ],
});

// Apply to data before passing to component
const originalData = fetchDataFromBackend();
const adaptedData = adapter.adaptData(originalData);

// Use with component
component.data = adaptedData;
```
